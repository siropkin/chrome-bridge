# chrome-bridge — agent instructions

**Driving Chrome for a user?** The operating manual is the skill: read [.claude/skills/chrome-bridge/SKILL.md](.claude/skills/chrome-bridge/SKILL.md). It links the [command reference](.claude/skills/chrome-bridge/reference/commands.md) and [recipes and gotchas](.claude/skills/chrome-bridge/reference/recipes.md). Run everything as `node <repo>/cli.mjs <command>`, where `<repo>` is the folder containing this file.

The rest of this file is for agents changing this repo.

## Developing

- Product bar: an AI-first, open-source tool that anyone — not only IT people — can install, use, update and uninstall, and that AI agents love to use. Judge every change against it: user-facing text in plain words with one obvious next action (no jargon), agent-facing output that names the next step.
- Run `node test/selftest.mjs` before pushing — hermetic (spawns its own server on a test port, needs no Chrome). To make it a hard gate, enable the pre-push hook once per clone: `git config core.hooksPath .githooks`.
- The selftest is also the drift gate: it parses `extension/background.js` and `extension/commands.js` with `node --check` (the fake extension never executes them, so nothing else would catch a syntax error), asserts package.json and extension/manifest.json versions match, pins the `extension/commands.js` registry to the cli USAGE (same names, each usage line = that command's USAGE synopsis; every `MUTATING` type is non-readOnly; the caller-JS commands — eval, wait --js — carry `pageCode`), compares the fenced block in `.claude/skills/chrome-bridge/reference/commands.md` against the cli USAGE, checks that both READMEs embed `docs/agent-setup.md` (the canonical agent-setup paste text) verbatim, and names-checks `.claude/skills/chrome-bridge/SKILL.md` against the cli USAGE commands (a `SKILL_OMITS` list holds the deliberate reference-only ones) plus its load-bearing flags.
- `extension/commands.js` is the shared command grammar: the registry of every command (group, scope, readOnly/destructive, diskBound, pageCode), the line tokenizer, and parse/render for browser commands. `cli.mjs` keeps the I/O, the transport and the local-only commands. It is a classic script that publishes `globalThis.BridgeCommands` (no Node APIs, no eval), so the service worker can `importScripts` it and Node loads it as a side-effect import; `test/commands.mjs` unit-tests it in a bare vm. Error strings and output must stay byte-identical — agents and docs quote them. It lives under `extension/`, so even a CLI-only edit there makes `health` warn unpacked dev profiles that extension code changed on disk, until `cli.mjs extreload`.
- Docs are load-bearing — agents read them as the operating manual, and doc drift is a real bug class here (the `--profile` name shipped without a single doc update). A command or behavior change ships with ALL doc updates in the same commit: README.md, README.zh-CN.md, the skill (`SKILL.md`, `reference/commands.md`, `reference/recipes.md`) — plus any error string that teaches usage. Keep SKILL.md lean: it loads on every browser task; depth goes in `reference/`.
- Onboarding has three entry points that must agree: `extension/setup-prompt.txt` (Web Store popup), `docs/agent-setup.md` (from source, embedded in both READMEs), and `install.sh` (by hand).
- Updates: `cli.mjs update` pins a Web Store user's checkout to the tag `v<their extension version>`, so every store upload must come from a pushed tag (the release workflow guarantees it — never upload a build by hand from an untagged commit). Version drift logic lives in `drift.mjs` (pure; the server feeds it, `update` plans with it).
- Extension change → bump the version in BOTH `extension/manifest.json` AND `package.json` (same value): `cli health` uses it to warn agents about a stale loaded extension, and same-version code drift is invisible to it. Then tag: `git tag -a vX.Y.Z -m "one-line summary"` — annotated, because the tag message is the release record (there is no CHANGELOG; the log is it). Pushing the tag triggers `.github/workflows/release.yml`: it creates the GitHub release (tag message as body, extension zip attached) and, when the `CHROME_PUBLISH` repo variable is set, uploads the extension to the Chrome Web Store as a draft. A pending CWS review locks the item (ITEM_NOT_UPDATABLE) — with the `CHROME_PUBLISHER_ID` secret set, the release cancels the pending submission itself before uploading (latest tag always wins); submitting for review stays a deliberate manual step on purpose (auto-submit would restart the review clock on every tag): once the draft is up, `gh workflow run cws-submit.yml` submits it (extensions can't script the dashboard, so agents can't click it). Never move a pushed tag.
- Commits: `area: what — why`; the body carries what it risked and where it was found live.
- Style: 2-space indent, single quotes, semicolons; long lines are fine — enforced by `.editorconfig` and habit, not a linter (there is none, on purpose: no config-free formatter is idempotent on this codebase).
- Manual fixture: `test/upload.html` (visible + hidden file inputs) for hand-checking `upload` against the real extension — the selftest's fake can't drive CDP file inputs.
- Real-extension gate: `test/stress/run.sh [section …]` drives the loaded extension end-to-end (two connected profiles for the multi-profile sections — profile 1 is the first connected, `STRESS_P1=<name>` pins it; profile 2 is never reloaded, since it may be another session's; profile 1's window visible for pixel/dialog/trusted — a preflight probe refuses the run up front when it's hidden, since those failures otherwise read like a product regression; `FX` overridable — the suite's :9334 server also serves the fixtures over HTTP; one left running from before an edit to `test/stress/server.mjs` is restarted, so new routes never 404). CI runs the single-profile sections on every push/PR and gates each release on them (`.github/workflows/stress.yml` — Chrome for Testing under xvfb; locally the same file covers everything). A red stress job on your change is yours to fix, not to merge around.
