# chrome-bridge — agent instructions

**Driving Chrome for a user?** The operating manual is the skill: read [.claude/skills/chrome-bridge/SKILL.md](.claude/skills/chrome-bridge/SKILL.md). It links the [command reference](.claude/skills/chrome-bridge/reference/commands.md) and [recipes and gotchas](.claude/skills/chrome-bridge/reference/recipes.md). Run everything as `node <repo>/cli.mjs <command>`, where `<repo>` is the folder containing this file.

The rest of this file is for agents changing this repo.

## Developing

- Run `node test/selftest.mjs` before pushing — hermetic (spawns its own server on a test port, needs no Chrome). To make it a hard gate, enable the pre-push hook once per clone: `git config core.hooksPath .githooks`.
- The selftest is also the drift gate: it parses `extension/background.js` with `node --check` (the fake extension never executes it, so nothing else would catch a syntax error), asserts package.json and extension/manifest.json versions match, compares the fenced block in `.claude/skills/chrome-bridge/reference/commands.md` against the cli USAGE, checks that both READMEs embed `docs/agent-setup.md` (the canonical agent-setup paste text) verbatim, and names-checks `.claude/skills/chrome-bridge/SKILL.md` against the cli USAGE commands (a `SKILL_OMITS` list holds the deliberate reference-only ones) plus its load-bearing flags.
- Docs are load-bearing — agents read them as the operating manual, and doc drift is a real bug class here (the `--profile` name shipped without a single doc update). A command or behavior change ships with ALL doc updates in the same commit: README.md, README.zh-CN.md, the skill (`SKILL.md`, `reference/commands.md`, `reference/recipes.md`) — plus any error string that teaches usage. Keep SKILL.md lean: it loads on every browser task; depth goes in `reference/`.
- Onboarding has three entry points that must agree: `extension/setup-prompt.txt` (Web Store popup), `docs/agent-setup.md` (from source, embedded in both READMEs), and `install.sh` (by hand).
- Extension change → bump the version in BOTH `extension/manifest.json` AND `package.json` (same value): `cli health` uses it to warn agents about a stale loaded extension, and same-version code drift is invisible to it. Then tag: `git tag -a vX.Y.Z -m "one-line summary"` — annotated, because the tag message is the release record (there is no CHANGELOG; the log is it). Pushing the tag triggers `.github/workflows/release.yml`: it creates the GitHub release (tag message as body, extension zip attached) and, when the `CHROME_PUBLISH` repo variable is set, uploads the extension to the Chrome Web Store as a draft. A pending CWS review locks the item (ITEM_NOT_UPDATABLE) — with the `CHROME_PUBLISHER_ID` secret set, the release cancels the pending submission itself before uploading (latest tag always wins); submitting for review stays a manual console click on purpose (auto-submit would restart the review clock on every tag). Never move a pushed tag.
- Commits: `area: what — why`; the body carries what it risked and where it was found live.
- Style: 2-space indent, single quotes, semicolons; long lines are fine — enforced by `.editorconfig` and habit, not a linter (there is none, on purpose: no config-free formatter is idempotent on this codebase).
- Manual fixture: `test/upload.html` (visible + hidden file inputs) for hand-checking `upload` against the real extension — the selftest's fake can't drive CDP file inputs.
- Real-extension gate: `test/stress/run.sh [section …]` drives the loaded extension end-to-end (two connected profiles for the multi-profile sections; profile 1's window visible for pixel/dialog; `FX` overridable — the suite's :9334 server also serves the fixtures over HTTP). CI runs the single-profile sections on every push/PR and gates each release on them (`.github/workflows/stress.yml` — Chrome for Testing under xvfb; locally the same file covers everything). A red stress job on your change is yours to fix, not to merge around.
